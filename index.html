The Physics of Memory: ECS vs OOP Spatial Benchmark

Published June 2026 • Verified on Apple M4 Pro (5,000 Entities)

When writing high-performance code in modern engines, we are no longer bottlenecked purely by raw CPU cycle speeds. Instead, we are bottlenecked by the speed of retrieving data from main memory. This spatial benchmark explores how data structures impact CPU cache behavior, pitting traditional Object-Oriented Programming (OOP) against a Data-Oriented Entity Component System (ECS) using a Sweep-and-Prune (S&P) collision engine.

Understanding the Simulation Modes

The performance of the Sweep-and-Prune (S&P) broadphase is likely heavily tied to spatial coherence—the frame-to-frame stability of entity coordinates. This benchmark allows you to toggle between three coherence profiles:

  • Wandering Mode (High Coherence): Entities move smoothly along continuous pathways. Because their relative order along the X-axis changes very little from frame to frame, the axis remains almost completely sorted. This allows the broadphase Insertion Sort to run in near-linear time ($O(n)$) in most frames. This represents typical real-time game simulation physics.
  • Erratic Mode (Low Coherence): Entities teleport randomly across the canvas each frame, simulating extreme scene changes. This typically breaks frame-to-frame spatial sorting. The broadphase is forced to re-sort the axis from scratch, degrading Insertion Sort to its worst-case quadratic complexity ($O(n^2)$) and showing how different memory layouts handle massive cache thrashing.
  • Static Mode (Absolute Coherence): Entities remain completely stationary. Positions never change, requiring zero sorting operations. This isolates the sweep overlap checks (AABB bounding box tests), indicating potential read-performance differences.

Key Takeaways & Technical Analysis

1. High Spatial Coherence Keeps Sorting Cheap ($O(n)$)

Under Static and Wandering modes, the circles maintain their spatial positions frame-to-frame. Because the list is already nearly sorted, S&P's sorting phase completes in near-linear time ($O(n)$). Here, the timed benchmark is likely dominated by the sweep phase (AABB overlap checks).

Even with sorting overhead minimized, the ECS implementations achieve up to a 3.56x speedup (with WASM ECS running at 0.307 ms vs OOP's 1.093 ms). Under OOP, resolving Y-overlaps likely requires dereferencing scattered heap objects to pull their `y` and `h` variables. In the ECS, these components are loaded contiguously from flat arrays.

2. The Cache Co-location Optimization

During early optimization, a pure Struct-of-Arrays (SoA) layout was used. However, it appeared that during the sweep overlap check, the CPU was likely making separate reads to independent `posY`, `w`, and `h` arrays.

To improve L1/L2 cache line efficiency, we redesigned the layout:

  • Isolated `posX` (Float64Array): Keeps sorting entirely contiguous, allowing the CPU to load exactly 8 X-coordinates per 64-byte cache line request.
  • Interleaved `posYwh` (Float64Array): Combines `y`, `w`, and `h` into a single packed array (`[y, w, h]` - 24 bytes per entity). When the sweep phase detects an X-axis overlap, the CPU can load the Y coordinate, width, and height together in a single cache line transaction, likely reducing extra memory hops.

3. Optimized Sorting Implementations

To ensure a fair comparison between the paradigms, the Sweep-and-Prune algorithms do not use basic, unoptimized sorting implementations. Instead, they use memory-aligned and hybrid strategies:

  • Memory-Optimized ECS Sorting: Rather than moving multi-component data dynamically on every swap, we sort a single flat index array (like an Int32Array) referencing the coordinates. This minimizes data writes and keeps iterations cache-friendly.
  • Hybrid Pivot Selection: Both native JavaScript and WASM (AssemblyScript) Quicksort implementations select a median/midpoint pivot to avoid worst-case $O(n^2)$ complexity on pre-sorted data. They also fall back to a tight Insertion Sort range once subarray sizes fall below 12 elements, avoiding V8/WASM function recursion overhead.
  • Double-Buffered (Ping-Pong) Mergesort: Our Mergesort implementations avoid copying elements back to the main array at the end of each merge step. By alternating source and destination buffers at each recursion level, we eliminate millions of array write operations per frame.

4. Erratic Mode: The Cache Miss Meltdown ($O(n^2)$)

Under Erratic mode, entities teleport randomly. This breaks spatial coherence and causes Insertion Sort to degrade to its worst-case quadratic complexity ($O(n^2)$). The CPU is then forced to perform millions of comparisons and swaps to re-sort the axis.

While both systems drop in performance, the ECS implementations maintain up to a massive 3.57x speedup (with WebAssembly ECS running at 3.510 ms vs OOP's 12.542 ms). In the OOP loop, swap operations involve moving references inside the scrambled `entities` array, which likely causes CPU cache stalls as the processor waits for RAM requests. In the ECS, the sort swaps integers in a flat contiguous `indices` array and checks positions in `posX`. The CPU pre-fetcher can load the X positions sequentially into cache, which likely allows the hardware to execute comparisons more efficiently.

5. OOP Tree vs ECS Tree: Flat BVH vs Pointer Chasing

To further illustrate the impact of memory layout, we compared two Bounding Volume Hierarchy solvers: **OOP Tree** and **ECS Custom Tree**. Theoretically, hierarchical bounding tree updates take $O(\log n)$ per entity, and overlap queries take $O(n \log n)$, which is algorithmically superior to Sweep-and-Prune's worst-case $O(n^2)$ in Erratic mode.

However, their memory layouts lead to vastly different CPU cache efficiencies:

  • OOP Tree (Pointer Chasing): The tree nodes are independent JavaScript objects allocated dynamically on the heap. Traversing this tree for overlap queries requires dereferencing node pointers sequentially. This "pointer-chasing" behavior causes severe cache thrashing, as node data is scrambled across the heap.
  • ECS Tree (Flat BVH): The tree nodes are packed into flat, contiguous typed arrays (`Int32Array`, `Float64Array`). Children and parents are referenced by flat array indices instead of heap pointers. Traversing the tree involves reading sequential elements, which matches the CPU's memory pre-fetch patterns and runs much faster than its OOP counterpart.

6. Scaling Limits: When $O(n \log n)$ Trees Overtake $O(n^2)$ S&P

While Sweep-and-Prune (S&P) dominates at smaller entity counts (5,000 entities) even under low coherence, algorithmic complexity eventually dominates memory layout efficiency as the simulation scales. The following table showcases a high-entity-count test (14,200 entities) in Erratic Mode:

Paradigm Runtime Algorithm Avg Frame Time 99th Percentile Speedup vs OOP S&P
ECS JS AABB Tree 16.007 ms 17.200 ms 6.21x
OOP JS AABB Tree 18.133 ms 24.500 ms 5.48x
ECS WASM Sweep & Prune 27.437 ms 28.300 ms 3.62x
ECS JS Sweep & Prune 37.769 ms 46.300 ms 2.63x
OOP JS Sweep & Prune 99.397 ms 219.400 ms 1.00x

At 14,200 entities under Erratic mode, the $O(n^2)$ sorting overhead of S&P becomes overwhelming (over 200 million possible index swap comparisons). Despite WASM S&P's cache efficiency, the $O(n \log n)$ tree-hierarchy implementations (both OOP and ECS Tree) run significantly faster. Notably, ECS Tree remains the absolute fastest overall (16.007 ms) by combining the algorithmic benefits of trees with a cache-friendly flat memory layout.
