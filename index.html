The Physics of Memory: ECS vs OOP Spatial Benchmark

Published June 2026 • Verified on Apple M4 Pro (15,000 Entities)

When writing high-performance physics or spatial engines on the web, execution speed is no longer limited purely by CPU instruction cycles. Instead, performance is governed by the time required to shuttle data from RAM into CPU caches. This live benchmark suite examines how data structures and algorithm choices dictate hardware cache behavior, pitting traditional Object-Oriented Programming (OOP) against Data-Oriented Entity Component Systems (ECS) across Javascript and WebAssembly.

Research Focus Outline

To cut through information overload, we analyze performance by testing one specific hypothesis at a time, culminating in a head-to-head showdown between the fastest broadphase engines at 15,000 active colliding entities:

  1. H1: Spatial Trees vs. Sweep & Prune
    Hypothesis: An $O(N \log N)$ spatial tree is always faster than $O(N^2)$ Sweep & Prune.
    Verdict: Almost always no! Contiguous array access in flat Sweep & Prune beats trees under normal coherent motion. Furthermore, equipping Sweep & Prune with Merge Sort makes it universally faster than spatial trees across all workloads, unless I'm running weirdly extreme chaotic simulations.
  2. H2: Sorting Strategies at Scale
    Hypothesis: Naive Insertion Sort ($O(N)$ nearly sorted) is optimal for real-time physics simulation.
    Verdict: Kinda! While Insertion Sort is technically fine for normal game workloads, I make Merge Sort my engine default. It provides rock-solid frame rate consistency across all scene types, avoiding catastrophic quadratic meltdowns during chaotic gameplay.
  3. H3: Javascript vs. WebAssembly
    Hypothesis: WebAssembly is required to realize the cache locality benefits of ECS.
    Verdict: False! Switching memory layout from AoS (Objects) to SoA (TypedArrays) in pure Javascript alone yields massive 3x to 22x speedups over traditional OOP.
  4. 🏆 Grand Finale: The Titan Showdown
    Question: What is the absolute fastest spatial broadphase algorithm on the web today?
    Verdict: Pitting the top spatial trees (WASM Tree, JS ECS Tree) head-to-head against the reigning Sweep & Prune champions (WASM Merge S&P, JS Merge S&P).

Technical Takeaways

1. Why I Make Merge Sort My Default

In everyday 2D game scenarios (under 5,000 entities), both Insertion Sort and Merge Sort execute in a tiny fraction of a millisecond. Nobody will ever notice the difference. However, the engineering argument for making **Merge Sort** my default is **frame rate consistency**. Under erratic scene changes at 15,000 bodies, naive Insertion Sort drops into a quadratic $O(N^2)$ meltdown: 43.16 ms (JS) and 128.47 ms (OOP)—slower than spatial trees (~19 ms).

By contrast, **Merge Sort** ($O(N \log N)$) streams contiguous cache lines with nearly 100% branch predictability. **Merge Sort Sweep & Prune** runs at 1.36 ms—over 13 times faster than WebAssembly spatial trees without any risk of sporadic frame rate meltdowns!

2. Struct-of-Arrays (SoA) Interleaving

To achieve these memory speeds in Javascript, we separate position coordinates (`posX` Float64Array) from bounding box dimensions. By interleaving `posY`, `width`, and `height` into a single packed array (`posYwh`), when the broadphase detects an X-axis overlap, the CPU loads the Y coordinate and dimensions together in a single 64-byte cache line request.
